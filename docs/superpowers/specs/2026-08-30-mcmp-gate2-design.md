# MCMP Gate 2 Design

Implements the Gate 2 stage of
`docs/superpowers/specs/2026-08-08-mcmp-ablation-harness-design.md`.
Conditions carried forward from `docs/MCMP_TIG_C004_REPORT.md` section 10.5.

## Purpose

Gate 1 established, on synthetic data, that MCMP's walk reaches documents FAISS
cannot — completely traversing a purpose-built chain at 192 agents in 12 of 12
seeds — while showing no advantage on a neutral control, and that its ranking
degrades as exploration grows. Two questions follow, and only real data answers
them:

1. **Structure.** Does real code retrieval geometry contain the chain structure
   the manifold fixture supplied? If it does not, the mechanism has nothing to act
   on and the synthetic result does not transfer.
2. **Scoring.** On real data, can MCMP's scoring hold onto what its walk finds?
   Section 10 showed discovery and ranking come apart; Gate 2 must measure them
   separately rather than reporting one retrieval number.

## Scope

In scope: a source-controlled judgement manifest derived from the call graph, an
embedding snapshot format with an offline test path, a real-data
`BenchmarkDataset` provider, a geometry characterisation stage, and a retrieval
stage that sweeps the agent budget.

Out of scope: TIG C004, any change to the production retriever, shared-colony or
query-colony designs, natural-language queries, and creating the production
embedding snapshot — that is a separate operational step behind its own gate.

## Non-goals

- Do not modify `benchmarks/mcmp/`. Gate 2 consumes its contracts and adapters
  unchanged; if a change there proves necessary, that is a separate spec.
- Do not resolve ambiguous call targets by guessing. Fail closed.
- Do not require a live embedding provider for any test or for repeated ablations.
- Do not draw a Gate 2 conclusion from the test snapshot. It exists to exercise
  the machinery, not to produce evidence.

## Architecture

New package `benchmarks/gate2/`, alongside `benchmarks/mcmp/`.

The load-bearing decision: **the existing `BenchmarkDataset` contract already
carries everything Gate 2 needs** — document ids, normalized vectors, query ids,
query vectors, and `relevant_by_query`. The real-data provider therefore emits a
`BenchmarkDataset`, and every existing adapter (A-E) and metric runs against it
unchanged. This is the original design's stated intent, that adapters expose one
result contract. It keeps the new code to five focused units.

```text
repo source --AST--> manifest (committed)
                          |
                          v
embedding snapshot --> provider --> BenchmarkDataset
                          |              |
                          |              +--> stage 2: adapters A-E + agent sweep
                          +--> stage 1: geometry characterisation (no MCMP)
```

### Corpus definition

A document is one function, async function, method, or class defined at module
level or in a class body, with its source text. Functions nested inside another
function belong to their parent document and are not separate documents. This is
the natural unit for a call graph; the existing 20-line fallback chunking is not,
because a chunk boundary cuts across call sites.

The corpus is `src/embeddinggemma/` of this repository: self-contained, pure
Python, present without any external dependency. Measured at the time of writing:
46 files, 229 functions and methods, 22 classes — about 251 documents, roughly
four times the synthetic fixture.

### Judgement manifest

Built by AST walk. For each definition, record the names it calls. Resolution is
**fail-closed on ambiguity**: a call name resolves only if exactly one definition
in the corpus carries that name. Measured on the corpus, 187 of 204 distinct
names (92%) are unambiguous; the remaining 8% are discarded rather than guessed.
No type inference is attempted, and that limitation is recorded in the manifest.

Relevance for a query document *q* is the union of its direct callers and direct
callees within the corpus, excluding *q* itself. Queries with no resolved
neighbours are excluded from the manifest.

The manifest is committed under `benchmarks/gate2/manifests/` and records the
repository commit sha it was derived from, the corpus root, the extraction
parameters, and per-document source location (file, line span, symbol name). It
is therefore re-derivable rather than an opaque frozen artifact.

### Embedding snapshot

One format, two provenances:

- **Test snapshot** — tiny, generated by a deterministic stub embedder, committed.
  Every test runs offline against it.
- **Production snapshot** — generated through the embedding-service, cached
  locally, gitignored for size. Its digest is recorded in the evidence.

A snapshot stores document ids, a float32 matrix, and metadata: backend
identifier, model identifier, dimension, creation timestamp, and the digest of the
manifest it was built for. The model identifier is read fail-closed: a client that
exposes none is rejected rather than recorded as "unknown". `EmbeddingServiceClient`
exposes no model id and the service does not report one, so production wraps it in
`ServiceEmbeddingClient(client, model_id=...)`, where the identifier is the
caller's explicit declaration. Loading a snapshot whose manifest digest does not match
the manifest in use is a hard error.

`src/embeddinggemma/mcmp/embeddings.py` is fail-closed HTTP against
`EMBEDDING_SERVICE_URL` with no local model fallback, and `models/embeddinggemma`
in this repository is incomplete — it has no top-level weights and no code path
loads it. There is consequently no offline production-embedding route, which is
precisely why the snapshot is materialised once and then reused.

### Stage 1: geometry characterisation

Runs on snapshot plus manifest, with no retrieval method involved.

1. **Relevant-rank distribution.** For each query, the similarity rank of each
   relevant document. This is the anti-degeneracy check: if relevant documents
   cluster at ranks 2-3 the way the legacy fixture did, the manifest is degenerate
   in the same way and that is visible *before* any method runs.
2. **Chain reachability.** For each relevant document ranked deeper than `top_k`,
   whether a path exists to it from the query in the mutual k-NN graph, of length
   at most `max_hops`, with each hop's similarity at or above `hop_threshold`.
   All four are CLI parameters recorded in the output; defaults `top_k = 8`,
   `knn_k = 8`, `max_hops = 6`, `hop_threshold = 0.0`. The default threshold of 0
   makes reachability purely a k-NN-graph property, so the measurement does not
   smuggle in a similarity assumption; raising it is available for sensitivity
   analysis.
3. **Manifold signature.** The fraction of relevant documents that are both far
   (deeper than `top_k`) and chain-reachable.

Output: `benchmarks/results/gate2/geometry-<manifest_id>.json`, carrying the raw
per-pair records, the full null distribution, and both sub-decisions, not only the
aggregates. The name carries the manifest, never a seed: stage 1 pools across its
own seed range and never reads `--seed`, so a seed in the name would correspond to
nothing inside the file.

**Stage 1 gate, pre-registered — amended 2026-08-30.** Stage 2 runs only if the
pooled manifold signature satisfies **both** of the following against a
permutation null:

1. It exceeds the **95th percentile** of the null distribution (one-sided test,
   `NULL_ALPHA = 0.05`, `NULL_PERMUTATIONS = 100`). The result is not noise.
2. It exceeds the null's **median by at least 10 percentage points**
   (`MIN_EXCESS_OVER_NULL_MEDIAN`). The effect is large enough to be worth the
   ~14 300x cost measured in Gate 1.

**The null:** the same pooled statistic, computed on the same geometry with the
relevance labels redrawn — for each query, as many documents as it really has,
drawn uniformly from the corpus. Vectors, query vectors and therefore the k-NN
graph are identical; only *which* documents count as relevant changes, and each
query keeps its set size so the pair count is unchanged. What survives the
comparison is the call-graph relation, isolated from graph density. The null is
pooled across the same seed range as the real statistic, or the two would not be
the same quantity.

**Why this replaced a bare threshold.** An earlier version of this section fixed a
10% floor with no reference point. Building the harness produced the measurement
that refutes it: on the test corpus — whose vectors are pure text digests with no
structure whatsoever — the pooled signature measures **0.356 to 0.444**, three to
four times that floor. A threshold that structureless input clears is not a gate,
and Gate 2 run against it would have reported "structure found" on noise. The
pre-registration principle stands; what changed is that the number is now
pre-registered *relative to a null the same data generates*, which is the only
form of it that can fail.

The earlier note in this section — that a *decision* threshold should be fixed in
advance, unlike a *generative* parameter — remains correct and is why both
constants above are fixed here rather than chosen after seeing the real corpus.

### Stage 2: retrieval

Methods A-E against the real `BenchmarkDataset`, through the existing adapters.

Per section 10.5, two requirements are binding:

- **Sweep the agent budget.** A single agent count reproduces exactly the error
  section 10 corrected. The sweep covers at least `{24, 48, 96, 192, 384}`, the
  range over which Gate 1 saw discovery saturate and ranking collapse.
- **Report discovery and ranking separately.** "Relevant documents reached as
  candidates" and "relevant documents ranked into the top k" are different
  quantities that diverge; collapsing them into one recall number hides the
  finding.

Output: `benchmarks/results/gate2/retrieval-<manifest>-a<agents>.json`, one file
per budget point.

## Data flow

```text
manifest builder (AST, committed output)
    -> snapshot builder (stub | embedding-service, cached)
        -> provider (BenchmarkDataset)
            -> stage 1 geometry -> geometry JSON -> gate decision
            -> stage 2 adapters A-E per agent budget -> retrieval JSON
```

## Reproducibility

The manifest records the source commit sha and extraction parameters. The snapshot
records backend, model, dimension and manifest digest. Every stage-2 run records
what Gate 1 already records, plus the manifest and snapshot digests.

A known limitation is inherited: `validate_gate1_evidence` compares environment
provenance against the running interpreter, so evidence generated elsewhere does
not replay. Gate 2 evidence carries the same property; it is recorded, not fixed
here.

## Failure handling

Ambiguous call targets are discarded. A query with no resolved neighbours is
excluded. A snapshot/manifest digest mismatch is a hard error. A missing
production snapshot is a clear error naming the operational step required, never
a silent fallback to the test snapshot.

## Test strategy

RED-GREEN per unit, following `tests/benchmarks/`. Everything offline.

- Manifest builder against a small package with a known, hand-checked call
  structure: correct edges, ambiguous names discarded, neighbourless queries
  excluded, deterministic output, commit sha recorded.
- Snapshot round-trip: write, load, digest mismatch rejected.
- Provider: emits a dataset that passes `BenchmarkDataset.validate()`, ids align
  with the manifest, vectors unit-normalized.
- Stage 1: rank distribution and chain reachability on a hand-constructed
  geometry with known answers, including a case with no chain and a case with one.
- Stage 2: A-E run end to end on the test snapshot; discovery and ranking are
  reported as separate fields.

## Decision gates

Stage 1 decides whether stage 2 is **run**, not whether it is **built**. The
implementation plan builds both stages; executing stage 2 against the production
snapshot is gated on stage 1's measured signature. Stage 2, if run, decides whether the
original spec's Gate 2 conclusion rule is met: proceed to shared-region or
query-colony design only if the labelled results show at least one reproducible
benefit attributable to MCMP or multi-query interaction, under explicitly reported
extra compute. If Multi-Query FAISS explains the benefit and MCMP adds none,
retain Multi-Query and stop MCMP index integration. A negative result at either
stage is a valid, complete answer.

## Deliverables

- `benchmarks/gate2/manifest.py`, `snapshot.py`, `provider.py`, `geometry.py`,
  `run_gate2.py`
- `benchmarks/gate2/manifests/` — committed judgement manifest
- `benchmarks/gate2/snapshots/` — committed test snapshot; production snapshots
  gitignored
- `tests/gate2/` — coverage per the test strategy
- findings appended to `docs/MCMP_TIG_C004_REPORT.md`, only after evidence exists
